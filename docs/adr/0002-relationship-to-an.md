# ADR 0002 — Relationship to `an` (structured animation)

**Context.** The user maintains `an`, a Python package for structured animation: a scene document, validated, rendered to video by swappable backends. Its targets differ from this project's: `an` makes videos of scenes; this project makes objects. They overlap in two places: both describe things by parameters, and both render animations of those parameters.

**Decision.**

1. This project's animation tracks use `an`'s model: a property path into the document, the actions `set` and `tween` with an easing, and combinators flattened to absolute times. The JSON shape is kept compatible so that a track written for one can be read by the other.
2. Neither project depends on the other. The link is a shared format and shared research, not an import.
3. Each project records the other: this ADR and the dev skill `shaping-dev-sibling-an` here; a short pointer in `an`'s own documentation, added by a session working in that repository.
4. Research to reuse from `an`: its reports on scene-graph and animation system design, on declarative parameter languages, and on animation interchange formats; and its golden-image approach to testing deterministic renders.
5. What `an` may want from here: turntable and parameter-sweep renders of 3D objects as assets for a scene, and the 2D-to-3D transforms as a way to give depth to flat artwork.

**Consequences.** A change to the track format in either project is a change to check against the other. The format is small on purpose.

**Amendment, 2026-10-14 (shaping#10).** `an` moved on: its timing contract now reads the authored flat timeline (`an.timeline` v1, rows of `{start, end, address, change}`), published with its easing table as the data-only npm package `@thorwhalen/an-contract` (`an`'s ADR 0006). shaping keeps storing tracks in the older flat-action shape, so saved designs need no migration, and exports them with `toAnTimeline` (`shaping/animate`). The differences, as the exporter resolves them: an address is `<target>:<property>` (optionally under an entity, `vase/view:azimuthDeg`); a null `from_value` means the value in the input design here and the value at the tween's start in `an`, so the exporter writes it when given the design; shaping's easings are cubic and `an`'s `ease_*` are quadratic, so the exporter writes exact cubic Béziers (and `ease_in_out` as two tweens), never the names; `fps` and `loop` have no place in `an`'s timeline and are dropped. Overlapping actions on one property mean different things in the two projects: `designAt` lets the action started last win for good, while `an`'s kernel (`evaluate_timeline`) holds active over held (an action playing wins over one that has ended, and among ended ones the latest end wins). The exporter therefore refuses two actions on one address that overlap beyond a shared instant, and refuses spans `an` cannot play (a tween with `end <= start`); on the tracks it accepts, both rules give the same values, which a test checks by evaluating the export with a port of `an`'s rule. No reader of `an.timeline` v1 exists on the `an` side yet (`an` writes the format; its compiler reads its own IR), so this overlap rule is pinned to `an`'s compiled kernel and must be rechecked when such a reader lands. The package is a devDependency read only by the tests, which validate the export against its `timeline.schema.json` and check every easing written against its `easing.json`; decision 2 still holds for code.

Status: accepted, 2026-09-29. Also recorded in `docs/architecture.md`.
